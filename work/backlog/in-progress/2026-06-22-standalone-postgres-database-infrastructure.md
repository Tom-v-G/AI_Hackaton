# Standalone Postgres Database Infrastructure

## Type

feature

## Context

`de_lekbak` currently stores viral CVE ranking data in an in-memory repository. The project should start moving toward standalone durable storage by copying or reimplementing useful database infrastructure patterns from `cve-intelligence` into `de_lekbak`, while preserving the strict boundary that `de_lekbak` must not import from, depend on, run against, or require `cve-intelligence` at runtime.

This first database story is intentionally infrastructure-only. It prepares `de_lekbak` for future viral CVE persistence, but it does not replace the current in-memory viral repository or introduce the full viral/NVD persistence model yet.

## Functional Requirements

- Add standalone database infrastructure for `de_lekbak` using Postgres only.
- Keep existing viral CVE API behavior working while storage remains in-memory for this story.
- Provide a foundation that future stories can use to persist viral CVEs, source mentions, refresh runs, and optional NVD enrichment inside `de_lekbak`.
- Preserve `de_lekbak` as an independently runnable application with no runtime dependency on `cve-intelligence`.

## Technical Requirements

- Copy or reimplement database infrastructure patterns from `cve-intelligence` into `de_lekbak/backend/de_lekbak_backend/`; copied code must use `de_lekbak_backend.*` imports and become owned by `de_lekbak`.
- Add async SQLAlchemy database infrastructure inside `de_lekbak`, including an async engine, async session factory, and request-scoped async session dependency suitable for future FastAPI repositories/services.
- Add a declarative ORM base and shared model mixins where useful for future `de_lekbak` models.
- Add Postgres-only database settings under the `DE_LEKBAK_` environment prefix, including database URL, pool size, max overflow, and SQL echo settings.
- Add the backend dependencies needed for async Postgres database access and migrations, including SQLAlchemy async support, asyncpg, and Alembic.
- Add Alembic configuration owned by `de_lekbak` and wired to `de_lekbak` model metadata.
- Generate and commit a first Alembic revision using autogeneration; it may be an empty baseline revision if no database models are introduced in this story.
- Do not copy the `cve-intelligence` NVD schema as the primary persistence model in this story.
- Do not replace `ViralCveRepository` with database-backed storage in this story.
- Do not add runtime imports from `cve-intelligence`, `app.*`, or path hacks that make `cve-intelligence` code importable from `de_lekbak`.

Technical decisions:

- Decision: implement Option B as a staged approach, starting with database infrastructure only.
- Rationale: `de_lekbak` needs durable storage, but the viral data model should be designed separately around viral rankings and mentions rather than copied blindly from the older NVD-focused app.
- Decision: use Postgres only for the database backend.
- Rationale: this matches the useful prior-art infrastructure in `cve-intelligence` and avoids adding multi-database complexity.
- Decision: include Alembic setup and a first autogenerated revision in this story.
- Rationale: migration tooling should be validated as part of the infrastructure foundation, even before substantive models are added.
- Decision: require future database model changes to use Alembic autogeneration as the starting point for migration revisions.
- Rationale: generated revisions reduce schema drift between ORM models and migrations while still allowing human review before commit.

Rejected alternatives:

- Rejected: copy the complete `cve-intelligence` NVD schema as the first persistence layer.
- Reason: `de_lekbak` is a viral CVE dashboard where NVD enrichment is optional, so the durable model should be designed around viral data in a later story.
- Rejected: make `de_lekbak` import or share database modules from `cve-intelligence`.
- Reason: this would violate the standalone runtime boundary defined for `de_lekbak`.
- Rejected: support SQLite in the first database infrastructure story.
- Reason: the user selected Postgres only.

## Acceptance Criteria

- `de_lekbak/backend` includes async Postgres database dependencies and configuration owned by `de_lekbak`.
- `de_lekbak_backend` exposes an async engine/session setup and FastAPI-compatible database session dependency without importing from `cve-intelligence`.
- `de_lekbak_backend` includes ORM base metadata suitable for Alembic autogeneration.
- Alembic is configured under `de_lekbak/backend` and targets `de_lekbak` model metadata.
- A first Alembic revision is generated with autogeneration and committed as part of the story.
- Existing viral CVE endpoints continue to work with the current in-memory repository.
- The implementation contains no imports from `cve-intelligence`, no `app.*` imports copied from the prior project, and no runtime requirement that `cve-intelligence` is running.
- Validation includes backend tests and linting from `de_lekbak/backend` plus a dependency-boundary check for accidental `cve-intelligence` imports.
